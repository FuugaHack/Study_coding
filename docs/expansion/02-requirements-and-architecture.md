# 02. 要件定義・技術選定・システム構成

## 1. プロダクトの目的

初心者が「ゲームを遊ぶ感覚」でプログラミングを始め、実践的な開発工程・資格・キャリアまで一貫して伸ばせる学習サービス。
1 回 3〜10 分の短時間学習 (主にスマホ) と、本格的なコーディング/プロジェクト学習 (主に PC) の両方を提供する。

## 2. 機能要件 (エピック)

| ID | エピック | 主要機能 | MVP 範囲 |
|---|---|---|---|
| E1 | 学習エンジン | コンテンツのサーバー管理・サーバー採点・進捗保存・バージョン管理 | M1 |
| E2 | ゲーミフィケーション | XP / レベル / ストリーク / デイリークエスト / コイン → バッジ / 実績 / ウィークリー / ボス戦 / フレンド | M1 → M2 |
| E3 | スキルツリー | 前提コースによる解放、ステージマップ表示、実力テストでスキップ | M1 (解放) → M2 (マップ/スキップ) |
| E4 | AI 回答レビュー | 多観点の構造化評価、段階ヒント、テストケース実行との併用 | M3 |
| E5 | AI 問題レビュー | 正確性/複数正解/陳腐化/難易度/重複/誤字のレビュー保存・再レビュー | M4 |
| E6 | 用語学習 | 用語マスタ、フラッシュカード / 選択 / 穴埋め / マッチング | M5 |
| E7 | 資格対策 | 試験範囲マスタ、分野別演習、模試 (タイマー)、苦手分析、SRS、逆算計画 | M6 |
| E8 | 開発工程コース・実践プロジェクト | 18 工程コース、架空クライアント案件、AI が PM/TL/レビュアー役 | M7 |
| E9 | パーソナライズ | 実力診断、キャリア別ロードマップ、AI メンター | M5〜M7 |
| E10 | モバイルアプリ | Expo (iOS/Android)、同一アカウント、通知、オフライン | M8 |

## 3. 非機能要件

| 項目 | 方針 |
|---|---|
| スケーラビリティ | 当面はモノリス (FastAPI 1 サービス + PostgreSQL + Redis)。AI 処理のみ非同期ワーカーへ切り出せる構造にしておく |
| セキュリティ | 正解データをクライアントに送らない (採点はサーバー)。JWT。ユーザーコードは隔離サンドボックスでのみ実行 |
| 不正対策 | XP は**サーバー判定のイベント**からのみ付与。冪等キーで二重付与を防止 |
| パフォーマンス | コンテンツは起動時ロード (メモリ常駐)。ユーザー進捗は 1 リクエスト 1〜3 クエリ |
| AI コスト | ユーザー単位レート制限 (既存)、結果キャッシュ、モデル使い分け、トークン計測 (M4) |
| 監視 | 構造化ログ (structlog は依存済み) → M4 で導入 |
| テスト | backend: pytest (PostgreSQL 実 DB) / frontend: typecheck + lint + build。CI で必須化 |
| 個人情報 | 収集はメール・ユーザー名のみ。学習ログはユーザー削除で CASCADE |
| コンテンツ版管理 | コンテンツは Git 管理の JSON。起動時にハッシュを計算し、回答ログに `content_version` を記録 |
| AI 誤評価対策 | 客観判定 (選択肢/テストケース) を優先し、AI 評価は補助。ユーザーの「評価に異議」報告 (M3) |

## 4. 技術選定 (ADR 要約)

| # | 決定 | 理由 | 却下した案 |
|---|---|---|---|
| ADR-1 | **既存スタック (FastAPI / React / PostgreSQL / Redis) を継続** | 既存資産・チームの習熟。規模に対して十分 | Next.js への全面移行 (メリットに対しコスト過大) |
| ADR-2 | **学習コンテンツは Git 管理の JSON (`apps/backend/app/content/`)** | レビュー可能 (PR で差分が見える)、バージョン管理が自然、DB マイグレーション不要 | DB 管理 + 管理画面 (編集者が増えた段階で再検討。AI 問題レビュー (M4) の結果は DB に保存) |
| ADR-3 | **XP は追記型の台帳 (`xp_events`) + 集計テーブル (`user_stats`)** | 冪等キーで二重付与防止、監査可能、後から集計し直せる | `users.xp` 列の直接加算 (不正/バグ時に追跡不能) |
| ADR-4 | **デイリークエストはコード定義 + 当日の回答ログから進捗を算出** | 状態テーブルが不要、定義変更が容易 | クエスト進捗テーブル (M2 でウィークリー/カスタム化する際に再検討) |
| ADR-5 | **日付境界は `APP_TIMEZONE` (既定 Asia/Tokyo)** | 主要ユーザーが日本。ユーザー別 TZ は M8 (モバイル) で追加 | UTC 固定 (JST 早朝が前日扱いになる) |
| ADR-6 | **モバイルは React Native + Expo** | TS/React の知識・`shared-types`・API クライアントを共有可能。EAS で両ストア配信 | Flutter (言語/型の共有不可)、ネイティブ 2 本 (工数 2 倍) |
| ADR-7 | **ユーザーコード実行は隔離コンテナ (Judge0 互換 or 自前 Docker + gVisor)** | 任意コード実行は API プロセスから必ず分離 | API プロセス内 `exec` (論外)、ブラウザ内 (Pyodide 等) は言語が限られる → 初心者向けの補助として併用可 |
| ADR-8 | **テストは実 PostgreSQL で実行** | モデルが PG 固有型に依存 (D8)。本番と同じ挙動 | SQLite (型非互換) |
| ADR-9 | **AI ワーカーのキューは PostgreSQL (`async_tasks` + `FOR UPDATE SKIP LOCKED`)** | インフラを増やさない。登録が API のトランザクションと一緒にコミットされる。既存のステータス API がこの表を読んでいる | SQS / Celery / arq (規模が大きくなったら SQS へ。`app/worker/queue.py` に閉じ込めてある) |

## 5. システム構成 (目標)

```
[Web (React)]  [Mobile (Expo)]            ← packages/shared-types, packages/api-client (M8)
        \           /
         [FastAPI API]  ── Redis (レート制限 / キャッシュ / ランキング)
          |    |   \
          |    |    └─ Worker (AI レビュー / 問題生成 / 問題品質レビュー)  ← M4 で分離
          |    └─ Sandbox Runner (コード実行, ネットワーク遮断)          ← M3
          └─ PostgreSQL (ユーザー・進捗・XP・レビュー結果)
Content: apps/backend/app/content/*.json (Git 管理, 起動時ロード)
AI: Amazon Bedrock (Claude)  ※有料。本番利用の契約・上限設定は要承認
```

## 6. ゲーミフィケーション設計原則

- **学習行動に報酬を結びつける**: XP は「正解」「新しい問題への挑戦」「復習」に付与。連打・同一問題の周回では増えない (初回正解のみ満額、以降は 1 日 1 回の少額)。
- **過度な競争を避ける**: ランキングは任意参加・フレンド内/同レベル帯のみ (M2)。課金要素は入れない。コインは見た目 (アバター) とストリーク保護にのみ使う。
- **失敗を罰しない**: 不正解で XP を減らさない。ハートや残機は導入しない。
- **経験者に配慮**: 実力テストで前提コースをスキップ可能 (M2)。
